## 2. 硬约束与推荐方案

硬约束包括：个人租户、普通用户可用所有功能、Sa-Token、BYOK 与 Token 面板、代码/配置/自定义前端插件、插件变更不重启主平台/全部 Runtime、管理员按版本审核公共资源、七阶段交付及 Docker Compose 部署。

推荐方案为 Java 21 与 Spring 生态、Vue 3 与 LogicFlow、模块化控制服务加独立执行进程、MySQL/Redis/OpenSearch/S3 兼容对象存储；默认 S3 实现建议 SeaweedFS。除 Sa-Token 和部署方式外，这些是当前蓝图建议，阶段 1 需要验证并锁定可兼容版本；不应直接把各组件官网的最新版本拼在一起。

## 3. 实施约定

技术正文中的模块、字段、事件、契约和目录是拟定设计，不是当前已存在 API。落地时每个 Issue 应说明采用的契约版本、失败行为、迁移影响和验证证据。修改技术细节可以由开发任务在约束内完成；涉及削减已确认功能、扩大数据范围或改变用户配置成本时，需要先形成明确变更记录。

外部资料仅用于支撑组件能力与协议事实；平台的授权、版本、状态和评测策略是本项目设计，不是第三方框架自动提供的保证。技术引用以官方文档为主，查阅日期为 2026-11-23；发行前再次核对版本、许可、镜像与支持范围。

## 4. 优先验证的架构风险

1. 同进程多租户模型配置是否存在缓存串用、流式用量缺失或跨租户回调问题。
2. Graph 编排适配能否保持平台自己的节点/版本契约，并可靠保存运行状态；框架内存示例不能作为恢复方案。
3. 插件代码、界面和配置能否独立加载，旧任务固定版本与当前撤权能否同时成立。
4. 公共资源是否通过单独可发布副本和读取路径避免未审核更新泄漏。
5. RAG 指标在不同切分方案下是否保持同一原文证据基准，Token 汇总是否避免父子重复。
6. Compose 的文件、数据、内部密钥和执行实例能否按声明重建、恢复与升级。

这些验证应转化为 [ci 模板](../ci/requirement-decomposition-template.md) 下的具体任务，不用空泛“后面再考虑”替代实现。

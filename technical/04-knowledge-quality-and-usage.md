# 知识工程、质量评测与 Token 用量

> 版本：v0.2 · 更新：2026-11-23 · 状态：拟实施方案与指标定义；未开展真实数据评测，不包含虚构提升结果。

本设计对应 [阶段 4](../requirements/phases/phase-04-knowledge-and-rag.md)、[阶段 5](../requirements/phases/phase-05-quality-prompt-cost.md) 和 [阶段 6](../requirements/phases/phase-06-publishing-and-operations.md) 的知识补全与运营需求。召回、答案质量、任务成功和费用分别观察，不能用一个分数掩盖失败。

## 1. 知识工程全链路

知识库有两条关联链路：离线资料版本流水线，以及在线查询和回答流水线。离线处理输出可检索、可引用的证据；在线过程必须能定位采用的资料版本和每次筛选、排序、截断。

| 环节 | 产生的对象 | 验证与失败处理 |
|---|---|---|
| 导入 | 原文件、来源元数据、内容摘要、所属租户/项目、资料版本 | 文件类型/大小/重复/损坏检查；每个文件独立状态 |
| 解析 | 规范化文本、标题、页/段/表位置、缺失标记 | 预览可与原文核对；部分失败不伪装完整成功 |
| 内容整理 | 去噪结果、结构信息、受控修正版本 | 不修改事实；修正保留原资料和变更依据 |
| 切分 | 片段、父段关系、原文锚点、策略版本 | 长度/标题结构/重叠可调，检查条件与表头是否割裂 |
| 索引 | 文本/向量索引版本、Embedding 模型与参数、过滤字段 | 维度和模型变更需要重建，不能把不兼容向量混在同一可用索引 |
| 激活 | 知识库当前可用版本与索引清单 | 全部必要步骤完成后切换；新版本失败时旧版本继续可用 |
| 撤权与删除 | 当前不可访问状态、清理任务与回执 | 先限制访问再清理派生数据；旧索引/缓存/下载不能绕过 |

S3 保存原文和必要处理结果，MySQL 保存权威版本与生命周期，OpenSearch 为派生索引。解析、OCR、Embedding、重排和评测调用都创建任务与调用明细；不把“知识处理后台任务”视为免费、不计量的工作。

阶段 4 交付文本、可提取文本 PDF、DOCX 等核心链路；扫描文本、表格结构和跨文档完整证据问答在阶段 6 必须收口。阶段 4 可提示这些输入的能力边界，但第六阶段不得继续标为可选。

## 2. 原文证据模型

每段证据用 documentId、documentVersion、页/段/表/单元格或字符区间以及内容摘要定位。chunkId 只是某个切分版本下的检索单元，不能作为长期唯一标准答案。调整切分后，新 chunk 映射回同一原文证据单位，评测才能比较。

表格需要保存标题、行列头、单位、合并单元格与必要脚注的对应关系；OCR 需要保存位置、置信/缺失信息及可复核图页。一个问题需要多个证据时，样本标注“哪些是必要证据、哪些是可替代支持”。同一段文字的重复索引不应被计算成找到了多个不同证据。

知识权限作用在原文、片段、向量、查询缓存、引用和导出。查询前进行范围过滤，返回证据和打开原文时再次核对当前授权。若权限差异使某问题对用户不可回答，应按其有权访问的语料和任务目标评价，不能把找到了其他租户资料作为召回提升。

## 3. 检索流水线与策略注册

一次查询保存原问题、受信运行上下文确定的执行租户/项目/获准资料范围及独立的访问者身份、知识版本、转换后的实际查询、候选来源及排序、过滤、融合、重排、扩展和最终上下文。策略注册表描述输入输出、所需模型/插件、参数、费用来源、可解释信息和版本；内置基础策略随平台交付。

| 策略 | 适合解决的问题 | 局限、成本与验证重点 | 交付定位 |
|---|---|---|---|
| 解析与清洗修复 | 原文缺字、顺序错误、标题和单位丢失 | 后续检索算法无法补回未进入语料的事实，先检查原文 | 阶段 4；OCR/表格阶段 6 |
| 按结构切分与合理重叠 | 条件被切断、上下文不足、片段太大 | 重叠增加索引和 Token；过大影响精确定位 | 阶段 4 内置 |
| 关键词 / BM25 | 编号、专名、缩写和精确表达 | 词法差异和语言分词影响结果；不能代替语义通道 | 阶段 4 内置 |
| 稠密向量 | 同义问法、自然语言意图 | 专有编码或领域迁移可能弱；Embedding 更换需要重建和对照 | 阶段 4 内置 |
| 混合检索 | 同时覆盖精确词和语义表达 | 候选去重和融合口径清楚；不要直接相加不同分数尺度 | 阶段 4 内置 |
| 元数据/版本过滤 | 业务日期、产品版本、限定知识源 | 错误过滤会减少可用证据；保留过滤前后可授权范围内的诊断信息 | 阶段 4 内置 |
| 查询改写 | 简略问法、别名、上下文指代 | 不能改变实体、时间、否定条件；保留原查询作对照 | 阶段 4 内置 |
| 多查询与子问题拆分 | 单个问法遗漏表达，问题含多个条件 | 增加检索/模型调用；控制数量并按原文证据去重 | 阶段 4 基础；多文档联验阶段 6 |
| 父段/相邻片段展开 | 检索命中细节但缺条件和上下文 | 展开仍需权限和 Token 预算，不能把邻近内容自动视为相关 | 阶段 4 内置必要证据补充 |
| 重排 | 相关证据已在候选中但顺序靠后 | 重排不能补回候选池之外的证据；另记时间、调用和最终 K | 阶段 4 内置可配置 |
| 上下文去重与证据选择 | 多通道重复、最终窗口被低价值片段占满 | 记录丢弃理由，比较进入模型的必要证据是否完整 | 阶段 4 内置 |
| 条件路由 | 不同知识类型适用不同策略 | 路由本身可能选错；应保留回退、样本分层和来源解释 | 阶段 4 简单选择，后续可扩展 |
| HyDE 等假设文档查询 | 稀疏问法与语料表达差异明显的实验场景 | 生成内容可能虚构，只能作检索信号，不能作为答案证据 | 扩展/实验策略，不是首版默认必需 |
| 检索专用模型训练、图检索 | 大量稳定标注或明确关系查询 | 数据、计算与维护成本高，需单独证据证明价值 | 后续研究/插件，不以名称堆叠代替核心质量 |

[OpenSearch 的 RRF 说明](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/rrf/) 提供按名次融合的实现依据。PeachAgent 可先以 RRF 作为混合基线，再用真实样本比较归一化加权方案；不把某种融合方法写成总能胜出的默认结论。RRF 分数也不是跨查询可比的“答案可信度”。

[HyDE 原始论文](https://aclanthology.org/2023.acl-long.99/) 使用生成的假设文档帮助寻找真实语料。这里将其列为可扩展实验，且明确生成文档不是事实证据；未验证时不能宣称它在用户语料上提高召回。

## 4. 如何判断漏召回发生在哪里

| 观察到的问题 | 首先检查 | 合理改动方向 | 不能直接得出的结论 |
|---|---|---|---|
| 原文有答案，但解析结果没有 | 格式、OCR、顺序、表头和丢页 | 修复解析、调整支持范围、补人工检查 | “换 Embedding 一定解决” |
| 解析有证据，候选没有 | 权限/版本过滤、词法表达、向量质量、候选数量 | 修正过滤、混合通道、改写、Embedding/切分实验 | “Rerank 不够强” |
| 候选有证据，前 K 名没有 | 融合、重复、排序和重排 | 调整融合或重排，检查是否挤掉必要多证据 | “资料还不够多” |
| 前 K 名有证据，模型上下文没有 | Token 预算、去重、截断、邻近展开 | 改证据选择和上下文组织 | “检索 Recall 已经证明答案应该正确” |
| 上下文完整，回答仍错 | 提示约束、模型、引用、任务要求 | 调整生成与证据使用，增加无答案处理 | “继续加大 topK 一定更好” |
| 回答正确但引用不支持 | 引用定位、生成后映射、拼接错误 | 原文锚点与引用校验 | “语言流畅就可算有依据” |

## 5. 评测样本与实验设计

每个样本至少保存问题/任务、来源、适用租户/权限、知识版本、是否可回答、必要/可替代证据、预期结果或判定规则、难度/类型、标注者和标注版本。数据集支持开发/优化、候选验证、最终独立检验三类用途：开发集用于分析失败和生成候选，验证集用于按预先确定的指标选优，最终检验集用于检验已选方案。小规模实验可明确声明简化划分，但不得把参与选优的样本继续称为独立最终检验；避免反复用检验集选择 Prompt、检索参数或评测器。

首批样本应包含实际业务常见问题、精确编号、同义问法、跨段条件、无答案、资料冲突/过期、权限不允许和恶意资料指令；阶段 6 加入扫描、表格和跨文档多证据。用线上失败样本扩充时，先脱敏并取得有权复用的范围，不把其他用户原始对话自动放进公共评测集。

对比时固定样本、语料快照、访问范围、分母口径、候选 K 与最终 K、上下文 Token 预算、生成模型和版本、参数以及评测器版本。若某项需要改变，记录为实验变量或单独实验组。固定随机种子只在供应商支持时可用，不能因此声称模型输出完全可复现。

成对实验保存每题 A/B 结果和失败类型；重要或波动较大的样本可重复运行，报告分布、置信区间或明确的小样本限制。按查询对做 bootstrap 等统计时，同一查询的重复尝试不能当作完全独立的新问题来夸大样本量。没有足够标注时只能报告“相对已标注证据的覆盖”，不能声称知道全部真实相关资料。

## 6. 指标定义与统计口径

令 G(q) 为问题 q 在指定语料/权限范围内经人工确认的相关证据单位集合，R_K(q) 为检索结果映射回原文后的前 K 个结果所覆盖的证据集合。平台保留 K 的原始检索单位、去重和证据映射规则。以下为本平台拟定指标契约，必须在报告中展示适用分母。

| 指标 | 定义与解释 | 使用限制 |
|---|---|---|
| Recall@K | 找到的标准证据数 / 标准证据总数，即交集大小除以 G 的大小 | G 为空时不定义为 0 或 1；单独列无答案问题。标注不全时只称已标注证据召回 |
| Hit@K | 前 K 内是否至少命中一个相关证据；跨问题取均值 | 命中一个不代表多证据任务完整 |
| 必要证据完整覆盖率 | 每题先判断全部必要证据组是否满足（0/1），再按适用问题汇总；替代证据按预先标注的组判定 | 必须定义必要组，不能事后改变答案依据来提高分数 |
| MRR@K | 第一个相关结果名次的倒数；未命中为 0，再跨问题平均 | 描述首次相关结果位置，不描述全部证据完整性 |
| Precision@K | 前 K 中相关结果比例，按声明的结果单位计算 | 需要足够相关性标注；未知相关性不能随意当作不相关或删去 |
| nDCG@K | 用预先定义的相关等级评价排序，并以理想排序归一化 | 仅在有可靠分级标签时提供，报告增益函数与截断口径 |
| Context Coverage | 真正送入模型的上下文覆盖的必要证据比例；展示分母及替代证据组判定方式 | 与候选 Recall 分开，反映重排和截断后的信息是否保留 |
| 答案正确 / 有依据 | 是否满足业务规则；每个重要结论是否有证据支持 | 与语言流畅性分开；部分正确、冲突和未知单独处理 |
| 引用准确 / 充分 | 引用定位是否有效、原文是否支持、关键结论是否都有支持 | 一个有效链接不代表所有结论都有依据 |
| 无答案处理 | 无充分证据时是否说明缺口，是否避免编造 | 不用将所有问题拒答来获得“低幻觉”表面优势 |
| 任务成功率 | 达到样本预先定义的业务目标的运行数 / 纳入评价的任务数 | 模型响应成功不等于业务目标完成；失败和取消处理规则提前定义 |

分别记录候选池、重排前 K、最终上下文的覆盖率，不能把三者都叫 Recall。重排固定候选池时，可能提高最终 topK 的召回或排序指标，但候选池覆盖没有增加。

**说明性例子，非实测结果：** 某问题需要证据甲、乙、丙。候选池找到了甲乙丙，但重排后只给模型甲乙，则候选召回为 3/3，最终上下文的 Context Coverage 为 2/3，该题必要证据完整覆盖为否（按题汇总记 0），Hit 为 1；不能据 Hit=1 宣称问题的证据已找全。如果只是增加 K 才包含丙，应同时报告更多上下文的成本与同预算结果。

报告同时给出宏平均、适用样本数、无答案/未标注/失败/未执行数量和类型分层。不能删除困难问题或服务失败后只对成功题平均，再称整个项目质量提高。

## 7. 质量中心的对象与判定方式

| 评测对象 | 可确定检查 | 需要判读或人工复核 | 关联阶段 |
|---|---|---|---|
| 工作流 | 图结构、输出字段、执行路径、预算、取消和重试事实 | 业务分支结果是否达到目标 | 2；5 批量 |
| Agent | 实际工具/参数、动作结果、停止原因、产物存在 | 任务是否完成、是否遗漏约束 | 3；5/6 联验 |
| RAG | 证据映射、版本、引用位置、检索指标 | 原文相关性、答案支持、必要证据组 | 4/5；6 扫描/表格 |
| Skill | 候选、选择、读取层级、文件范围、脚本授权 | 选择理由是否符合任务，是否过度/不足读取 | 3/5 |
| 上下文压缩 | 保护字段/待办/权限/效果状态是否保留、回读是否成功 | 摘要是否改变事实或不确定性，后续任务是否退化 | 3/5 |
| 工具与插件 | 契约、版本、授权、隔离、错误传播、模型用量归集 | 业务动作是否符合声明，界面是否误导 | 3/5/6 |
| 多 Agent | 子任务关系、重复调用、预算、汇合、权限传播 | 分工是否有帮助，冲突是否被正确处理 | 5 建指标，6 真实联验 |
| 发布与部署 | 公开状态、调用身份、持久化、启动和恢复结果 | 交付说明是否足够完成使用路径 | 6/7 |

规则检查优先用于可确定事实，模型评审适用于语义判读，人工复核处理关键结论、争议与校准。评审模型也使用本人 BYOK、记录版本/Prompt/费用；没有配置评审模型时仍可做确定性和人工评测，不能转用平台公共 Key。

模型评审采用明示量表、证据引用、允许“不足以判断”，对一组人工标注样本检验一致性。对比候选时可隐藏名称、交换展示顺序以检查位置偏差；评审服务失败记录为失败，不默认打零分代表答案差。人工改判保留原判、理由、改判者与时间。

项目看板分别展示任务效果、检索/引用、可靠性、授权与隔离、延迟、Token/费用和覆盖度。可以根据业务明示权重计算辅助分数，但关键权限泄漏、无法恢复或业务致命错误不能被其他维度高分抵消。是否发布以已确认需求和明确验收结论为准。

## 8. Prompt 优化闭环

1. 选择固定基线、目标指标、允许改变的范围和优化预算。系统约束、权限边界和必要格式列为不可被候选移除的部分。
2. 在开发集上分析失败模式，生成并初筛有限候选，展示内容差异、变量变化与适用原因。
3. 对候选做结构和约束校验，然后运行可比较的样本；生成候选、评测和评审的调用都计入优化任务。
4. 在候选验证集按约定指标选择候选，确定方案后在最终保留检验集验证一次或按预先声明程序验证，报告改善、回归、时长与消耗；最终检验结果不反向进入本轮优化。
5. 用户明确采用候选，创建新资源/应用版本；基线保留可回退，发布依赖不被静默更新。
6. 达到预算或没有足够改善时停止，保留已完成实验与原版，不将“生成了新 Prompt”当作优化成功。

首版提供可理解的内置闭环；特定优化算法可作为插件扩展，但必须遵守同样的样本隔离、账本和采用规则。

## 9. Token 账本：所有入口统一计量

每次外部模型请求生成唯一调用记录，不按 UI 页面或根任务重复记账。请求来源覆盖对话、Agent 步骤、工作流节点、Skill/插件内受控模型调用、Embedding、查询改写、重排模型、摘要压缩、评测器和 Prompt 优化。非模型工具、传统 OCR 或不返回 Token 的重排服务按页、条、次数、秒等实际单位记录。

| 字段组 | 拟定字段或内容 | 约束 |
|---|---|---|
| 归属 | invocationId、attemptId、runId、parentRunId、rootRunId、tenantId、projectId、applicationRelease、pluginVersion | 身份由受信运行上下文注入，不能让插件伪造其他租户 |
| 调用事实 | provider、model、endpointType、开始/结束时间、状态、供应商请求 ID | 重试是新尝试，补报更新同一调用而不新增重复费用 |
| 原始用量 | 供应商报告字段、计量单位、返回时点、适配器版本 | 脱敏后保留足以复核的原始统计，不混入秘密 |
| 规范化用量 | input、output、total、cachedInput、cacheWrite、reasoningOutput 等适用字段及包含关系 | 只有依据供应商定义才能建立子项关系；不支持字段为未知/不适用 |
| 统计状态 | reported、estimated、pending、unknown、not_applicable | 各字段独立标记；报告值替换同字段估算的当前累计值，原估算仅留依据；缺失不能填 0 |
| 金额 | 价格版本、有效时点、币种、计价单位、估算金额或未知原因 | 金额是辅助估算，不能声称等于供应商最终账单 |
| 来源维度 | chat、agent、rag_ingest、rag_query、compression、evaluation、optimization 等 | 一个调用可以有标签，但账本主事实只能累计一次 |

归一化规则是供应商适配契约，不能对所有供应商硬编码 input+cachedInput+output+reasoningOutput。**示例，非供应商账单：** 若某供应商的 input=1000 已包含 cachedInput=600，output=200 已包含 reasoningOutput=80，则总 Token 是 1200，不是 1880。若缓存输入价格单列，适用金额可按 400 普通输入、600 缓存输入和 200 输出分别计价，推理子项不再加一次；其他供应商的包含关系必须另行验证。

流式响应可能只在末尾返回统计，用户取消、超时或网络中断后仍可能产生费用。未收到报告时保留 pending/unknown；能通过供应商记录补回时更新原调用。平台展示“停止新增调用”与“外部已发生但暂不明确的消耗”，不承诺取消必然退款。

## 10. 面板、汇总与预算

### 10.1 Token 面板

面板从个人总览进入，按时间、项目、应用/发布版本、运行、模型/供应商、任务类型、插件和状态筛选。展示输入/输出及适用子项、未知/估算占比、调用次数、失败/取消尝试、延迟和可得金额；支持定位到运行与调用明细、按权限导出。

同一调用的同一统计量只有一个当前累计值：已报告值替换该字段估算值，估算保留历史依据但不再次累加。输入已报告而输出缺失时，输出及总量仍按依据标为估计/未知，不能整条调用一律标成已报告。

父任务总量由其下所有唯一调用明细汇总，子任务明细可展开。按应用或插件分组是同一事实的不同视图，不能把根任务已汇总数与子任务数再相加。跨币种金额分别显示；价格缺失显示未知费用，不掩盖已有 Token。每成功任务费用按 PA-P5-012 纳入同一评价范围内的失败尝试开销，成功数为零时显示不适用；未知金额另列，不能只累加成功任务美化成本。

公共模板安装后的调用归使用者执行租户。作者明确发布托管应用时，按发布授权锁定的执行租户/凭证记账，另记外部访问者与渠道；不能把外部调用者的身份自动当作模型凭证所有者。详见 [发布设计](05-public-repository-and-application-release.md)。

### 10.2 并发预算

每次调用前按输入估算、最大输出和适用价格申请预留，支持 Token、调用次数、时间、并发和金额等不同限制。对同一运行和租户的并发申请使用原子准入；结束后结算报告值并释放未用预留，未知调用按保守策略保留或标记待核实，不能因超时立即当作零开销释放全部预算。

任务预算包括子 Agent、子流程、重试、摘要和评测子任务，不能通过拆任务逃逸。预算不足时停止启动新受限操作并显示原因，已经发出的请求按实际状态处理。计量不完整、估算误差或供应商异步计费时，预算是平台准入约束，不是供应商账单绝对封顶保证。

### 10.3 插件内模型调用

SDK 提供受控模型调用能力，调用方通过当前任务绑定的 Model Gateway 请求模型，不直接获得平台中所有密钥。模型类插件必须声明计量和能力映射，未经支持的统计标明未知。外部服务在自身内部调用模型但不返回使用量时，平台只能统计已知接口次数和已知费用，不能声称知道其内部 Token。

如果某扩展不能通过受控能力报告已声明的模型调用来源，应在安装/兼容校验中明确不满足该计量能力，不能悄悄从全局面板遗漏再宣传“全部调用已精准统计”。

## 11. 评测结果如何驱动研发

质量报告关联需求编号、应用/知识/插件版本、实验条件、逐题错误及调用明细。失败样本可以生成改进候选任务，但创建真实 GitHub Issue 仍按 [AI 执行指南](../ci/ai-execution-guide.md) 查重和拆分，不能让每次模型评分都自动制造 Issue。

优先修复证据链已经定位的瓶颈：解析缺失先修解析，候选缺失再改检索，排序缺陷改重排，生成误用改模型/提示约束，重复计量修账本。每次宣称改进需有条件一致的前后对比与退化清单；对于样本不足或结果不确定，结论应如实保留限制。

## 12. 分期验收重点

| 阶段 | 最小必需证据 |
|---|---|
| 1–3 | 真实调用明细、报告/估算/未知状态、父子/重试汇总、权限与预算；Skill 和压缩事件可追溯 |
| 4 | 原文标注、资料/切分版本、逐题检索记录、固定条件小规模对照、更新/删除/撤权 |
| 5 | 独立样本、指标分母、逐题比较、人工校准、Prompt 候选采用与回退、完整 Token 面板 |
| 6 | 扫描/表格/跨文档、多 Agent/长任务、公共资源与托管发布身份下的评测和计量 |
| 7 | 恢复后的资料锚点、版本、评测证据和调用账本可查；新运行不重复计算旧账本 |

数值目标应由实际业务样本和基线决定。本设计不预填“召回提升 20%”“成功率 99%”或固定模型评分作为既定验收结果。

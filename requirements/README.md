# PeachAgent 需求文档

> 版本：v0.1 · 更新：2026-11-23 · 状态：需求草案，待项目负责人确认。

这里描述 PeachAgent **需要解决什么问题、用户应当完成什么任务、怎样判断交付是否达标**。所有产品能力仍处于规划阶段，文档合并不代表功能已实现。

## 阶段需求

| 阶段 | 文档 | 交付结果 | 当前状态 |
|---|---|---|---|
| 1 | [项目与对话](phases/phase-01-project-and-chat.md) | 能在项目中完成一次可追踪、有用量与预算约束的对话 | 待确认，未开发 |
| 2 | [可视化工作流](phases/phase-02-visual-workflow.md) | 能拖拽、配置、运行和调试一个有条件分支的工作流 | 待确认，未开发 |
| 3 | [Agent、Skill 与上下文](phases/phase-03-agent-skills-context.md) | 能让 Agent 使用授权工具与按需读取的指导完成有限多步任务 | 待确认，未开发 |
| 4 | [知识库与 RAG](phases/phase-04-knowledge-and-rag.md) | 能从自己的资料中检索证据、生成带引用的答案并检查检索效果 | 待确认，未开发 |
| 5 | [质量、Prompt 与成本](phases/phase-05-quality-prompt-cost.md) | 能用固定依据比较效果、验证优化并衡量成本 | 待确认，未开发 |
| 6 | [高级协作与扩展](phases/phase-06-advanced-collaboration.md) | 按实际需求增强人工介入、长任务、协作和受控执行 | 后续规划，待选择范围 |

阶段 1–5 是首个完整核心版本的范围；阶段 6 为后续增强。首个能运行的成果在阶段 1 交付，无需等所有阶段全部结束。

## 文档约定

- `PA-P1-001` 一类编号标识阶段需求；`PA-COM-001` 一类编号标识共性需求。编号在修改标题时保持稳定。
- `-A1` 一类后缀标识该需求的验收条目；阶段中的任务包编号是 **候选开发拆分**，不代表 GitHub Issue 已创建。
- “必须”表示纳入已确认阶段范围后需要满足的行为；“候选”“后续”“待确认”不能作为已经交付的能力展示。
- 各阶段继承共性需求；不能因为阶段文档未重复书写权限、预算或保密要求，就将其省略。
- 文档中的操作名称表达用户意图，不规定页面布局、接口路径、代码结构或存储方式。
- 需求文档中的质量指标是验收口径，不是实测成绩或性能承诺。

## 如何提出修改

对具体需求提出变更时，注明需求编号、当前问题、期望行为、影响阶段及验收标准变化。范围调整应同时更新路线图、需求追踪和[总规划 Issue #1](https://github.com/Ryan-Guizhou/PeachAgent/issues/1)。

需求确认后，按 [开发流程](../ci/README.md) 将候选任务转为开发 Issue，再补充必要技术设计。目前 `technical/` 仅预留目录。

| D-007 | 个人用户作为租户，可使用全部平台功能 | 首期不建设企业组织层级或商业套餐限制；仍需要资源隔离与管理员治理 |
| D-008 | 权限校验采用 Sa-Token | 用户指定框架；租户资源归属和执行授权仍是产品与应用必须落实的职责 |
| D-009 | 用户自行配置模型及外部凭证 | 平台不提供统一模型池/余额；公共资源不可传播作者密钥 |
| D-010 | 必须提供 Token 消耗面板 | 自首次调用开始记录，覆盖 Agent、RAG、评测、优化、压缩和插件模型调用 |
| D-011 | 所有人可以提交共享资源，管理员审核后公开 | 应用模板、插件、Skill、MCP、Prompt 模板纳入同一机制；审核绑定版本 |
| D-012 | 审核通过的公开资源对所有正常用户可见 | 未审核草稿和作者私有数据仍不可见；公开可见与执行权限、第三方账号授权分别处理 |
| D-013 | AI 按 ci 模板执行需求拆分和开发管理 | 总 Issue → 差量拆分 → 单 Issue 开发/PR → 适用编译通过 → 合并 main → 每期核对 |
| D-014 | 增加第七阶段，使用 Docker / Docker Compose 部署 | 用户只需配置数据库和中间件密码；常规挂载、初始化、内部密钥和服务编排由交付包处理 |
| D-015 | 当前先完善文档并提交 GitHub | 当前不实现整个平台或伪造可运行部署包；本次工作由 Issue #4 和对应 PR 追踪 |

这些决策来自当前会话的连续确认，不需要逐个重新询问用户。新增与这些约束冲突的设计应先说明影响，再申请范围变更。

## 2. 本方案采用的默认解释

| 事项 | 当前解释 | 为什么这样约束 |
|---|---|---|
| 全部功能可用 | 普通个人租户可以使用各产品功能；资源和执行仍受本人授权与合理额度限制 | 功能开放不等于可以查看他人私有资料或无限使用公共资源 |
| 私有与公开插件 | 私有安装自助；公开版本必须审核；两种情况均遵守执行授权与隔离 | 避免个人调试被公共审核流程卡住，也避免审核替代运行权限 |
| 共享应用 | 默认提供可安装/复制的模板，使用者绑定自己的凭证 | 避免开放目录变成作者密钥和模型余额的共享入口 |
| 对外运行应用 | 由应用所有者显式开放调用入口，明确执行租户、访问凭证、预算和调用记录 | Web/API/Webhook 调用与公共模板目录是不同产品行为 |
| 不重启 Runtime | 主平台和全局 Runtime 不因插件生命周期操作重启；受影响实例可替换 | 将可验收承诺与“所有插件进程永不重启”的不现实解释区分 |
| 审核新版本 | 新内容、代码、界面和权限变更提交新候选版本，原已批准版本不被暗中覆盖 | 管理员批准的是可识别的内容，不是一张永久通行证 |
| 一键部署 | 在满足文档前提的单机上，填写密码后一条辅助启动命令完成编排与初始化 | Docker 安装、硬件、网络和可获取镜像是环境条件；不能宣称无条件自动成功 |

## 3. 技术推荐与待验证事项

具体实现选型由 [技术总架构](../technical/01-platform-architecture.md) 提出，不写成用户已经指定或平台已经具备的能力。技术依赖的版本、许可、交付物可获得性、适配成本和容量应在阶段 1 的技术验证及阶段 7 的发行验证中锁定。

| 待落实事项 | 处理阶段 | 对当前文档工作的影响 |
|---|---|---|
| 框架版本组合、模型厂商能力矩阵、任务状态保存与恢复可行性 | 阶段 1 | 不阻塞需求与架构文档；开发前给出兼容性实证 |
| 插件执行语言首批集合及 SDK 兼容窗口 | 阶段 1–3 | 先形成明确支持范围的参考实现；未验收语言不得被宣传为默认均支持 |
| 真实用户资料、RAG 标注集、业务成功判定规则 | 阶段 4–5 | 先规定样本结构和比较方法，不能编造召回提升数字 |
| 数据保留期限、账号自助注册策略、默认并发和预算 | 阶段 1/6 | 设置可解释的保守默认，发布前在管理员设置和验收材料记录 |
| 正式安装包可获得性、受支持机器、最低规格和公网可信访问方式 | 阶段 7 | 在实际部署验证后公布，不把猜测值写成安装保证 |

这些是后续开发任务应解决的设计细节，不是现在停下来要求用户重复确认的理由。

## 4. 变更管理规则

保留已有需求编号的含义，新增行为追加编号；删除或拆分需记录替代关系。一次范围变更同步更新需求、产品架构、路线图、技术影响、任务依赖、总 Issue 与验收覆盖。不能只改一个章节，让其他文档继续承诺旧行为。

需求确认与技术实现验证分别记录。若某个框架不支持硬要求，应先寻找满足需求的适配方案；确实需要削减功能时，提交具体影响、替代方式与代价，获得用户确认后更新范围。性能、召回率和费用结论只能来自真实样本和实际运行。

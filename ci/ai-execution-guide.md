# AI 按模板执行指南

> 版本：v0.2 · 更新：2026-11-23
>
> 本指南是执行规约，不是当前已经部署的自动化服务。当前产品功能尚未实现；本轮只修改文档。

## 1. 执行目标与权限

AI 的目标是把已授权需求推进到可核查交付，持续保留需求、Issue、PR 和实际结果之间的关系。用户已确认的范围和操作授权持续有效，不为每个普通动作重复询问；遇到真正缺失的决策或超出授权的动作才提出具体问题。

本项目已确定：个人用户作为租户使用完整功能；用户自己的模型和工具凭证由本人在 UI 配置；公共应用、插件、Skill、MCP、Prompt 的指定版本经过管理员审批后才公开可见；自定义配置插件、代码插件和前端扩展支持动态管理。六期完成产品，第七期完成 Docker Compose 部署。任务不能擅自删减这些范围。

## 2. 每次开始先读取

1. 当前用户指令与已确认决定，判断本次是文档、功能、修复还是部署交付。
2. 适用需求与验收项、总体架构和相关技术文档；只有文档无法解释时再补充必要研究。
3. 总规划、对应开发 Issue、相关 PR、需求追踪和阶段验收。
4. 当前分支、main、实际文件与构建入口；不把旧对话里的路径和命令当作现状。

无 Issue 或需求变更需要重拆时，先用[拆分模板](requirement-decomposition-template.md)比对已有任务。现有任务已覆盖的工作不重复创建。

## 3. 选择可以执行的任务

判断当前任务真正依赖什么。依赖已经满足的任务继续执行；互不影响的任务可以并行。共享文件、契约和迁移需要协调，不能互相覆盖。

仅对阻塞当前任务的缺口等待或提问；其他无关任务、全量 CI 或未来阶段待决事项，不应成为统一停止理由。自己的 PR 仍必须通过必要构建和验收。

## 4. 开发与自查

| 步骤 | 必须产出 |
|---|---|
| 建立对应分支 | 明确的 Issue 关联与最新基线 |
| 完成约定范围 | 正常、失败及适用权限/预算/版本行为，而非仅页面或占位 |
| 更新文档 | 与实际行为匹配的使用和技术说明，不伪造兼容性 |
| 自查差异 | 无明显错误、敏感资料、无关文件或破坏性修改 |
| 实际验证 | 命令、环境、输入、结果、提交版本与必要日志 |

测试和检查应解决实际风险。纯文档检查内容、链接和图示；代码必须真实编译，必要的运行场景不能省略；部署任务必须验证实际部署包，不能只校验 YAML 后宣称可上线。

失败时先定位并修复授权范围内的问题。环境或外部资源阻塞无法消除时，说明已完成、未完成、错误依据和继续条件，不写虚假通过。

## 5. 提交与合并

一项 Issue 提交一份 PR，按 [PR 模板](pull-request-template.md)写清原因、变更、验证和影响。相关开发 Issue 完整解决时使用 `Closes`，总规划使用 `Refs #1`。

在已有明确授权且必要检查通过时，继续合并 main；不要固定在每项工作后询问“是否继续”。如仓库权限或明确审批要求阻止操作，说明具体阻塞并保留可审查结果，不能绕过限制。

合并后核验 main 内容和提交。合并改变已验证内容时补做受影响检查。更新对应 Issue、追踪表和总规划，不把一个 PR 合并自动换算为阶段全部完成。

## 6. 阶段和整体验收

每期使用[阶段核对模板](phase-review-template.md)。阶段 1—6 全部产品能力必须核对，尤其是动态插件及前端、个人租户 BYOK、公共版本审批、质量与成本闭环。

阶段 7 使用[发布部署验收模板](release-acceptance-template.md)，核实部署者仅配置必要中间件密码即可按约定入口启动，默认挂载、初始化、健康、凭证保存和完整功能都成立。首次启动、再次启动、重启、升级、备份恢复分别验证，不能混为一项。

总规划保持开放直到七阶段承诺全部有验收证据。未完成项、未经批准的延期或未知结果必须保留。

## 7. 结束或交接记录

记录以下事实，便于下次直接续接：

- 实际完成的需求、Issue、PR 和 main 提交。
- 已执行检查及结果，未执行检查及原因。
- 未完成事项、阻塞和已确认的范围调整。
- 下一项可执行任务和已满足的依赖。

任务仍在授权范围内且没有真实阻塞时继续推进；只有阶段目标已完成、用户要求停止，或确实需要用户输入才能继续时才结束当前工作。
